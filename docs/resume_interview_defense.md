## 0. 开场总述

### 30 秒自我介绍

我叫唐轲，本科是宁夏大学机械工程，研究生在东南大学机械工程，研究方向偏深度学习、二维材料图像识别和边缘部署。我的项目主线有两个：一个是二维材料显微图像实时识别系统，偏 Python、PyQt5、PyTorch、OpenCV 和相机 SDK 二次开发；另一个是 RK3588 边缘端多路视频智能分析系统，偏 C++、FFmpeg、Rockchip MPP、RKNN 和 RTMP 推流。我的优势是既能训练和评估视觉模型，也能把模型接到真实采集、推理、显示、保存和端侧部署链路里。

### 2 分钟项目串讲

我做的二维材料项目主要解决显微镜下 MoS2、WS2、Graphene 等材料的层数识别问题。二维材料的单层、少层、多层差异往往是颜色、纹理和边界上的细微变化，所以我没有把它建模成普通目标检测，而是做像素级语义分割。系统上，我用 ctypes 封装 Toupcam 相机 SDK，实现相机枚举、打开、分辨率切换、曝光、增益和白平衡控制；界面层用 PyQt5 做双窗口显示；推理层单独用 QThread 跑模型，采用最新帧覆盖旧帧策略，避免推理慢时 UI 卡顿。模型是 RepELA-Net，前两级用 RepConv 提取局部纹理，后两级用 ELA 做轻量注意力，全局建模，再通过 DW-MFF 和边界增强模块融合多尺度特征。最终模型 2.12M 参数，8.28MB，512 输入下 FLOPs 5.28G，最优测试 mIoU 84.64%，Pixel Acc 98.08%，Mean F1 91.16%。桌面端支持原图/检测图双窗口、类别筛选、检测框和置信度叠加、结果保存和 AVI 录制。

第二个 RK3588 项目是把多路视频分析放到边缘端。流程是 FFmpeg 负责 MP4 拆包，MPP 做 H.264 硬解码，解码后的帧进入 RKNN 多模型推理，包括人员、安全帽、打电话/玩手机等模型。后处理阶段对不同模型输出做置信度过滤、NMS、IoM 嵌套关联和类别融合，再把多路画面拼成 2x2 合成画面，最后通过 MPP 硬编码成 H.264 并通过 RTMP 推送到服务端。这个项目更侧重 C++ 工程、多线程队列、NPU 资源分配和端侧实时性。

可能追问：Python 项目里怎么保证实时性？

回答：

避免把所有操作放在 UI 主线程。相机抓帧、模型推理、UI 刷新分开；推理线程只处理最新帧，不排队积压；OpenCV 和 PyTorch 的底层计算本身会释放一部分 GIL，所以合理拆线程能明显改善界面响应。

### “多线程”

回答核心：

我理解的多线程不是简单开几个线程，而是根据生产者/消费者关系拆分任务，并控制队列长度、锁粒度和旧帧丢弃策略。二维材料项目里相机线程不断采集最新帧，UI 定时器只读最新帧显示，推理线程异步消费帧；如果推理没跟上，旧帧会被覆盖，系统优先保证当前画面低延迟。

常见追问：为什么不把所有帧排队？

回答：

实时检测里排队会让系统越来越延迟，比如现在看到的是 1 秒前的检测结果，用户体验反而更差。显微观察和视频分析更关注当前状态，所以采用 bounded queue 或 latest-frame 策略，只保留最新帧。

### “CMake”

回答口径：

CMake 主要用于 C++ 边缘端项目组织，管理 FFmpeg、MPP、RKNN、librtmp 等库的 include 路径、链接库和编译选项。面试时可以讲：我会把不同模块拆成 decode、inference、postprocess、render、streamer 等 target，然后通过 `target_link_libraries` 链接对应依赖，避免所有源码堆在一个命令里。

可能追问：Debug/Release 有什么区别？

回答：

Debug 保留符号、便于 gdb 定位；Release 开优化，性能测试必须用 Release。边缘端视频项目里如果用 Debug 跑实时指标，延迟和 CPU 占用会偏高，不适合作最终性能结论。

### “Linux 常用命令及脚本开发”

回答口径：

我常用 Linux 做环境部署、日志排查和脚本化训练/运行，比如 `ps/top/htop` 看进程和资源，`grep/awk/sed` 过滤日志，`scp/rsync` 传模型，`ssh` 远程调试，`chmod` 和 `systemctl` 管服务，shell 脚本批量启动训练、评估和推理任务。

### “RK3588”

回答核心：

RK3588 是 Rockchip 的边缘计算平台，适合视频解码、NPU 推理和端侧部署。它的典型资源包括 CPU、GPU、NPU 和 VPU/编解码单元。项目里不要把所有事情都丢给 CPU：视频解码用 MPP，模型推理用 RKNN/NPU，编码推流也尽量走 MPP，这样 CPU 主要负责调度、后处理和业务逻辑。

### “NPU 异构计算”

回答核心：

异构计算就是把不同类型任务放到最适合的硬件上。CPU 负责控制流、队列、后处理；NPU 跑神经网络；VPU/MPP 做编解码；如果有 RGA 或类似图像加速模块，可以做 resize、格式转换和图像拷贝。关键是减少 CPU 拷贝和避免某个模块成为瓶颈。

可能追问：NPU 多核心怎么用？

回答：

一般做法是为不同模型或不同流创建 RKNN runtime 实例，并设置 core mask，把模型实例绑定到不同 NPU core；同时用线程池调度输入帧。需要注意 RKNN context 通常不能随便跨线程共享，最好每个 worker 持有自己的上下文或明确加锁。

### “MPP 编解码”

回答核心：

MPP 是 Rockchip 的硬件编解码接口。解码端把 H.264 packet 送入 MPP decoder，输出 NV12 等格式的硬件帧；编码端把合成后的画面送入 MPP encoder，输出 H.264 packet。使用 MPP 的目的就是降低 CPU 占用，提高多路视频实时性。

可能追问：为什么不用 OpenCV 直接读视频？

回答：

OpenCV 方便，但多路 H.264 视频如果靠 CPU 解码，很容易占满 CPU。边缘设备上应尽量用 MPP 硬解码，这样 CPU 只做调度和后处理，系统可扩展性更好。

### “端侧模型量化、转换与部署流程”

回答流程：

1. 训练阶段得到 PyTorch `.pth`。
2. 推理部署前切换 deploy 模式，比如 RepConv 多分支融合。
3. 导出 ONNX，固定输入尺寸，避免动态 shape。
4. 用 onnx-simplifier 简化图。
5. 用 rknn-toolkit2 配置 target platform、mean/std、量化 dataset。
6. build 生成 `.rknn`。
7. 在 RK3588 端用 rknn-lite2 加载模型，初始化 runtime，设置 NPU core，执行 inference。
8. 对输出做后处理并接入业务系统。

本地代码依据：`F:\Code\Windows_train\OrangePiCamera\PhysicalNet\export_onnx.py` 和 `F:\Code\Windows_train\OrangePiCamera\PhysicalNet\convert_rknn.py` 已经体现了 PyTorch -> ONNX -> RKNN 的转换流程。

## 4. 项目一：二维材料显微图像实时识别系统

项目名称建议口径：2DMatScope，面向二维材料显微图像的实时语义分割与检测可视化系统。

### 4.1 “南京大学二维材料与智能表征课题组 计算机视觉算法开发实习生”

面试官可能问：你在团队里负责什么？

回答：

我主要负责视觉算法和应用系统打通：包括二维材料显微图像分割模型 RepELA-Net 的训练、评估、可视化，显微相机 SDK 接入，PyQt5 桌面端检测系统开发，推理线程优化，结果保存与录制。简单说，我不是只训练模型，而是把模型接到真实相机和用户界面里。

### 4.2 “开发面向 MoS2、WS2、Graphene 等二维材料显微图像的实时识别系统”

面试官可能问：这三种材料都完全做了吗？

稳妥回答：

主系统默认按 MoS2/WS2 这类 4 类层数标签运行：背景、单层、少层、多层。Graphene 在迁移学习代码中支持 3 类或合并类标签，比如 BG、1L、>1L 或 BG、FL、ML。桌面端默认 UI 是 4 类，如果部署 Graphene，需要根据 checkpoint 的类别数动态配置 class names 和颜色表。这个是我能明确说的工程边界。

### 4.3 “显微相机采集”

实现：

相机采集由 `CameraController` 封装。程序启动时加载 `nncam.dll`，用 ctypes 声明 SDK 函数签名，再执行：

1. `Toupcam_EnumV2` 枚举设备。
2. `Toupcam_Open` 打开第一个相机。
3. `Toupcam_put_eSize` 设置分辨率。
4. `Toupcam_StartPullModeWithCallback` 进入回调采集模式。
5. 图像事件到来后，后台线程调用 `Toupcam_PullImage` 拉取一帧。
6. BGRA buffer 转成 OpenCV BGR numpy 数组。

面试追问：为什么用 ctypes？

回答：

相机 SDK 提供的是 C/C++ 动态库接口，Python 没有现成高级封装，所以用 ctypes 直接加载 DLL、声明参数类型和返回值。这样不需要重新编 C++ wrapper，适合快速把硬件接入 PyQt/Python 应用。

### 4.4 “图像增强”

实现：

图像增强包括 USM 锐化、Gamma 校正和 CLAHE。USM 用高斯模糊图与原图加权，强化边缘；Gamma 用 LUT 调亮或压暗；CLAHE 在 LAB 色彩空间增强 L 通道的局部对比度。增强主要服务于显微观察和截图展示，推理默认用原始帧，避免增强参数改变模型输入分布。

追问：为什么不把增强后图像送进模型？

回答：

如果训练时没有用同样增强，推理时强行增强可能造成域偏移。我的处理是显示增强和模型推理解耦：用户可以调显示效果，但模型输入尽量保持和训练数据一致。

### 4.5 “轻量化语义分割”

回答核心：

二维材料层数识别不是简单框选问题，单层、少层、多层边界很细，而且区域形状不规则，所以底层任务更适合语义分割。模型输出每个像素属于哪一类，然后为了用户查看方便，再从 mask 中提取连通区域画检测框和置信度。

### 4.6 “检测结果可视化与结果保存闭环”

实现：

推理线程输出 `pred_mask` 和 `conf_map`。UI 线程把 mask 映射成颜色图，与原图按 alpha 融合；对每个类别做连通域分析，小区域过滤，保留区域画边框、类别名和平均置信度；左下角叠加层数统计。保存时支持原图和检测图，完整模式会把比例尺、FPS、Latency 一起画进去，简洁模式会另存同名 `.txt` 记录元数据。

### 4.7 “用于判别二维材料单层、少层和多层区域”

面试官可能问：标签怎么定义？

回答：

语义分割标签是 0 背景、1 单层、2 少层、3 多层。训练时每张图有对应 PNG mask，像素值就是类别 id。模型最终输出 `[B, 4, H, W]` logits，softmax 后每个像素取最大概率对应类别。

### 4.8 “相机枚举、分辨率切换、曝光/增益控制、白平衡调节”

实现细节：

枚举相机：`Toupcam_EnumV2` 返回设备列表。

分辨率切换：UI 下拉框有 `2560x1922`、`1280x960`、`640x480`，切换时调用 `Toupcam_put_eSize`，如果相机正在运行则先 stop 再重启。

曝光：自动曝光调用 `Toupcam_put_AutoExpoEnable`，手动曝光调用 `Toupcam_put_ExpoTime`。

增益：调用 `Toupcam_put_ExpoAGain`。

白平衡：手动调用 `Toupcam_put_TempTint`，自动白平衡调用 `Toupcam_AwbOnePush`。

### 4.9 “曝光 1-2000ms、增益 100%-500%、色温 2000-15000、Tint 200-2500”

回答：

这些范围来自 UI 控件与 SDK 范围限制。曝光在 UI 以毫秒显示，传入 SDK 时乘 1000 转成微秒；代码里会根据 SDK 返回的最大最小曝光范围做 clamp。增益、色温和 Tint 同样会在设置前限制到合法区间。

追问：为什么要 clamp？

回答：

因为 UI 输入和硬件合法范围可能不一致，如果不 clamp，轻则 SDK 返回错误，重则相机状态异常。硬件控制一定要做边界保护。

### 4.10 “基于 PyQt5 设计相机抓帧、UI 刷新、模型推理分离的多线程架构”

线程拆分：

1. 相机抓帧线程：轮询 SDK，有新图就更新 `_latest_frame`。
2. UI 主线程：QTimer 每 16ms 取最新帧显示，刷新状态栏。
3. 推理线程：QThread 后台执行预处理、滑窗推理、后处理。
4. 模型加载线程：加载 `.pth` 时不阻塞 UI。

回答重点：

PyQt GUI 不能在主线程里做耗时推理，否则窗口会卡死；所以相机、模型加载和推理都要异步化。

### 4.11 “最新帧覆盖旧帧策略降低界面卡顿”

实现：

相机线程只保存一个 `_latest_frame`，新帧来了直接覆盖；推理线程 `submit_frame()` 也只保存一个 `_frame`，如果上一次还没处理完，新提交的帧会覆盖旧帧。

面试官可能问：这会不会丢帧？

回答：

会丢帧，但这是实时系统主动取舍。显微实时检测更关注当前画面，不需要把历史每帧都算完。如果排队不丢帧，会导致检测结果越来越滞后，用户看到的可能是几秒前的画面。

### 4.12 “512×512 滑窗推理”

实现：

模型训练 crop 是 512，所以推理时把大图切成 512×512 patch。每个 patch 单独送入模型，输出概率图；重叠区域累加概率并除以 count，得到平均概率，再 argmax。

窗口数量示例：

640×480：padding 到至少 512，高宽方向大约 2 个 crop。

1280×960：默认 stride 384，约 3×3，共 9 个 crop。

2560×1922：约 5×7，共 35 个 crop，所以延迟明显增加。

追问：为什么不用整图推理？

回答：

整图推理会受显存、输入尺寸和训练分布影响。滑窗能保持训练和推理输入一致，也能处理任意分辨率；缺点是高分辨率 crop 数量多，延迟上升。

### 4.13 “EMA=0.3 时序平滑”

实现：

推理线程保存上一帧的概率图 `_ema_probs`。当前帧概率 `cur_probs` 到来后：

`ema = 0.3 * cur_probs + 0.7 * history`

然后再 argmax 得到 mask。

回答：

这不是训练权重 EMA，而是推理结果的时序平滑。显微镜画面会有轻微抖动或噪声，直接逐帧 argmax 会导致 mask 闪烁。EMA 让结果更稳定。

### 4.14 “0.4 置信度阈值过滤”

实现：

对每个像素取最大 softmax 概率作为置信度，如果小于 0.4，就把该像素归为背景。

回答：

阈值过滤主要抑制低置信噪声和散点误检。阈值太高会漏掉颜色很淡的单层区域，太低会引入噪声，所以 0.4 是在召回和误检之间的折中。

### 4.15 “RepELA-Net 轻量化模型”

一句话：

RepELA-Net 是一个轻量级语义分割网络，针对二维材料显微图像的小数据、细边界、多尺度区域特点设计。

结构：

输入 RGB 图像，扩展为 4 通道；stem 卷积降采样；stage1、stage2 使用 RepConv 提取局部纹理；stage3、stage4 使用 ELA 做全局上下文建模；decoder 用 DW-MFF 融合多尺度特征，最后上采样回原图大小输出 4 类 logits。

### 4.16 “RepConv”

回答：

RepConv 是重参数化卷积。训练时有 3×3、1×1、identity+BN 多分支，提升表达能力；推理时把 Conv+BN 融合，再把 1×1 padding 成 3×3，和 identity 分支相加，最后等价成一个 3×3 卷积。好处是训练时强、推理时快。

追问：融合公式？

回答：

Conv+BN 融合时，卷积权重乘以 `gamma / sqrt(var + eps)`，bias 变成 `beta - mean * gamma / sqrt(var + eps)`。多个分支融合后权重和 bias 直接相加。

### 4.17 “ELA”

回答：

ELA 是 Efficient Linear Attention。二维材料图像里既有很小的单层区域，也有大面积多层区域，需要全局上下文。标准 self-attention 是 O(N²)，对高分辨率不友好；ELA 用线性注意力近似，把复杂度降下来，同时通过多尺度 Q pooling 捕获不同尺度信息。

### 4.18 “DW-MFF”

回答：

DW-MFF 是 Dynamic Weighted Multi-scale Feature Fusion。encoder 会产生不同尺度特征，浅层细节多、深层语义强。DW-MFF 先用 1×1 卷积把通道对齐，再从深到浅逐级上采样融合。融合权重是可学习的，网络可以自动判断当前尺度更依赖深层语义还是浅层边界。

### 4.19 “边界增强模块”

回答：

二维材料层间边界非常淡，容易被平滑掉。边界增强模块通过 depthwise conv 学习边缘响应，再结合 channel attention，对边界区域特征加权增强。这样有助于区分单层/少层/多层交界处。

### 4.20 “模型参数量 2.12M、大小 8.28MB、FLOPs 5.28G”

回答：

参数量是统计模型所有可学习参数；模型大小是保存 state_dict 后的磁盘大小；FLOPs 是用 512×512 输入统计的运算量。简历里这组数字对应 RepELA-Small 代表模型，来自 benchmark 结果。

注意边界：

模型结构注释里早期目标写过小于 2G FLOPs，但最终 RepELA-Small 实测是 5.28G。面试时按实测数字说，不要说“我一定做到 2G 以下”。

### 4.21 “84.64% mIoU、98.08% Pixel Acc、91.16% Mean F1”

回答：

这组是 test set 上最优 seed=123 的结果。mIoU 是四个类别 IoU 平均，Pixel Acc 是所有像素中预测正确的比例，Mean F1 是各类别 F1 平均。由于背景像素很多，Pixel Acc 会很高，所以我更关注 mIoU 和少数类的 IoU。

追问：为什么不用 Pixel Acc 作为主要指标？

回答：

背景占比很高，模型全预测背景也可能有不错 Pixel Acc，但对单层/少层没有意义。mIoU 对各类更公平，更能反映分割质量。

### 4.22 “训练模型集成到桌面端检测系统”

实现：

训练得到 `best_model.pth` 后，GUI 里根据模型 variant 构造 `repela_net_small/tiny/base`，加载 checkpoint 的 `model` 权重，设置 eval 模式，然后交给推理线程。若是 deploy state_dict，会根据 key 里是否有 `fused_conv` 判断 deploy 模型。

### 4.23 “原图/检测图双窗口显示”

实现：

左侧 ImageLabel 显示 `current_frame` 或增强后的 frame；右侧 ImageLabel 显示 overlay 后的 `detection_result`。图像显示时 BGR 转 RGB，再转 QImage/QPixmap，并保持等比例缩放。

### 4.24 “类别筛选”

实现：

UI 下拉框 Full/Monolayer/Fewlayer/Multilayer 映射为 `None`、`{1}`、`{2}`、`{3}`。overlay 时只显示指定类别的 mask 和连通域框。

### 4.25 “检测框/置信度/层数统计叠加”

实现：

检测框不是模型直接输出，而是对分割 mask 做连通域分析。每个连通域统计面积、外接矩形和平均置信度；面积低于 500 像素过滤。层数统计是统计每个类别保留下来的连通域数量，并绘制到左下角。

### 4.26 “结果保存和 AVI 录制”

实现：

结果保存用 OpenCV `cv2.imwrite`。录像用 `cv2.VideoWriter`，编码 fourcc 是 XVID，保存两个 AVI：一个相机原图，一个检测结果图。录制 FPS 优先用当前显示 FPS，否则默认 15 FPS。

### 4.27 “640×480 延迟 38-58ms、显示帧率 30.4-47.7 FPS；1280×960 延迟 248-312ms”

回答：

这些是桌面端实测结果，记录在保存结果的 `.txt` 元数据里。这里的 FPS 是显示/采集刷新帧率，不等于模型每秒完整推理次数。推理延迟是单次异步推理耗时。因为采用最新帧覆盖，1280×960 下即使推理延迟较高，界面显示仍能保持流畅。

追问：为什么 1280×960 延迟高这么多？

回答：

因为滑窗数量从 640×480 的约 2 个 crop 增加到 1280×960 的约 9 个 crop，模型前向次数增加，延迟自然上升。

### 4.28 “技术栈：Python、PyQt5、PyTorch、OpenCV、Ctypes、相机 SDK 二次开发”

Python：整体应用、训练脚本和工具脚本。

### 4.29 项目一常见拷打题

问题：为什么不用 YOLO？

回答：

YOLO 输出框，适合目标位置检测；二维材料层数区域是不规则形状，而且边界和面积信息很重要。用语义分割可以得到像素级区域，再从 mask 生成框用于展示，所以分割更符合任务本质。

问题：你的模型比 FPN/MobileNetV2 mIoU 低，优势在哪里？

回答：

是的，预训练 FPN/MobileNetV2 的 mIoU 更高。我的模型优势在参数量、模型大小和显存占用更低，而且 RepELA-Net 是从头训练、没有 ImageNet 预训练。在轻量化和无预训练条件下，它用 2.12M 参数达到 84.64% 最优测试 mIoU。面试时我不会说它绝对精度最高，而是说它是轻量化和可部署方向的尝试。

问题：有哪些不足？

回答：

第一，GUI 和研究代码目前耦合较强，模型加载通过路径引入 RepELA-Net；第二，滑窗推理逻辑在 GUI、训练和推理脚本里有重复，后续应该抽成统一 inference API；第三，Graphene 的 3 类配置还没有在 GUI 层完全动态化；第四，高分辨率下滑窗数量多，实时性下降，后续可以做 TensorRT/RKNN/ONNXRuntime 或降分辨率策略优化。

## 5. 项目二：RK3588 边缘端多路视频智能分析系统

说明：当前 `2DMatScope` 工作区没有该项目完整源码；本节按简历描述对应的工程实现链路整理。另一个本地目录 `F:\Code\Windows_train\OrangePiCamera` 有 RKNN 转换、RKNNLite 加载、NPU 推理线程等相关代码，可作为“模型量化转换与 RKNN 部署”部分的依据。

### 5.1 “面向工厂安防、人员行为识别及多路视频监控场景”

回答：

这个项目的业务目标是把多路监控视频在边缘设备上本地分析，不把所有原始视频传到云端。典型任务包括检测人员、安全帽、打电话或玩手机等风险行为，然后把带检测结果的合成画面回传。

面试官可能问：为什么要边缘端？

回答：

多路视频上传云端带宽大、延迟高，也有隐私风险。边缘端本地解码和推理，只上传分析后的合成流，能降低带宽和延迟。

### 5.2 “基于 RK3588 边缘计算平台”

回答：

RK3588 适合这个项目，因为它有视频编解码能力和 NPU。项目里 CPU 不负责所有重活：H.264 解码和编码交给 MPP，模型推理交给 RKNN/NPU，CPU 负责调度、队列、后处理和推流控制。

### 5.3 “本地 MP4 视频接入”

实现口径：

用 FFmpeg 打开本地 MP4 文件，`avformat_open_input` 读取容器信息，`avformat_find_stream_info` 找到视频流，循环 `av_read_frame` 拿到 AVPacket。只取视频流 packet，送给 MPP 解码器。MP4 文件只是输入源，架构上后续也可以扩展 RTSP 或摄像头。

追问：FFmpeg 在这里负责解码吗？

回答：

不主要负责解码。FFmpeg 负责 demux，也就是从 MP4 容器中拆出 H.264 packet；真正的视频解码交给 Rockchip MPP 硬解码。

### 5.4 “MPP 硬件解码”

实现口径：

创建 MPP decoder context，初始化为 H.264 解码模式。FFmpeg 拿到的 packet 封装成 MppPacket，送入 `decode_put_packet`，再从 `decode_get_frame` 取出 MppFrame。解码输出通常是 NV12/YUV 格式，后续要做 resize、颜色转换和模型输入预处理。

关键点：

解码器要处理 info_change 事件，因为视频分辨率、stride、buffer group 需要在解码器真正知道流信息后配置。多路视频时，每一路最好有独立 decoder context 和队列。

### 5.5 “RKNN 多模型并行推理”

实现口径：

每个检测模型先从训练框架导出 ONNX，再用 rknn-toolkit2 转成 `.rknn`，部署端使用 rknn-lite2 加载。运行时为人员检测、安全帽检测、行为检测等模型分别创建 RKNN context，根据 NPU core mask 分配到不同核心，外层用线程池调度不同视频帧和不同模型。

本地代码可引用：

`OrangePiCamera` 里有 `.rknn` 加载、`RKNNLite().load_rknn()`、`init_runtime()`、推理线程和滑窗 RKNN 推理逻辑。这能说明你做过 RKNN 模型端侧部署流程。

### 5.6 “检测结果融合”

回答：

多模型输出不是简单拼起来，因为人员框、安全帽框、手机/打电话框之间存在包含关系和重复框。后处理先按置信度过滤，再做 NMS 去掉同类重复框，然后用 IoM 判断小目标是否嵌套在人员框里，最后根据类别规则融合成业务结果。

IoU 和 IoM 区别：

IoU 是交集 / 并集，适合判断两个相近大小的框是否重复。

IoM 是交集 / min(面积A, 面积B)，适合判断一个小框是否在大框里面。比如安全帽框在人员框里，用 IoM 比 IoU 更合理，因为安全帽很小，和整个人的 IoU 本来就低。

### 5.7 “多路画面拼接”

实现口径：

每一路推理和绘制后的画面先 resize 到统一子窗口大小，再拷贝到大画布的对应区域，比如 2×2 网格。拼接时要注意每路画面的框坐标已经在子画面坐标系内，若先画框再 resize，框和图一起缩放；若先 resize 再画框，则需要按缩放比例修正坐标。

### 5.8 “RTMP 推流”

实现口径：

渲染后的 2×2 合成画面进入编码队列，MPP encoder 编成 H.264 packet，再通过 RTMP 推到流媒体服务端。推流线程独立运行，避免网络抖动阻塞推理主流程。队列过长时丢弃旧合成帧，保证推流实时性。

追问：为什么要丢帧？

回答：

实时视频系统最怕延迟堆积。队列越来越长时，即使每帧都推上去了，用户看到的也是几秒前画面。丢掉旧帧保留最新帧，可以牺牲完整性换实时性。

### 5.9 “使用 FFmpeg 完成 MP4 视频流拆包”

回答：

FFmpeg 负责容器层处理。MP4 里面包含视频流、音频流、时间戳等信息。我们只取视频流 packet，并保持 PTS/DTS 信息，后面用于同步和推流时间戳。如果直接把 MP4 当裸 H.264 读，会丢失容器层信息。

### 5.10 “结合 Rockchip MPP 实现 H.264 硬件解码”

回答：

H.264 是压缩码流，模型不能直接处理，需要先解码成图像帧。MPP 硬解码可以把这一步放到硬件视频单元上，降低 CPU 占用。多路视频时这是关键，否则 CPU 解码会成为瓶颈。

### 5.11 “推流端通过 MPP 硬编码输出 H.264 视频流”

回答：

推流时不能直接推原始 RGB 帧，因为带宽太大。需要把合成画面编码成 H.264。用 MPP 硬编码可以降低 CPU 占用，保证多路推流稳定。编码时要设置分辨率、码率、帧率、GOP、profile 等参数。

### 5.12 “降低 CPU 占用并提升实时性”

回答：

优化来自三方面：硬解码减少 CPU 解码负载；NPU 推理减少 CPU/GPU 推理负载；硬编码减少 CPU 编码负载。CPU 主要用于调度、后处理和业务逻辑，这样多路视频才跑得动。

### 5.13 “部署人员检测、安全帽检测、打电话/玩手机检测等 RKNN 模型”

回答：

不同模型关注不同目标。人员检测先确定人在哪里，安全帽检测识别防护装备，打电话/玩手机检测识别风险行为。多模型拆分的好处是模型职责清晰、可以独立更新；缺点是推理次数增加，所以需要 NPU 核心分配和线程池调度。

### 5.14 “按 NPU 核心分配模型实例”

回答：

RKNN runtime 支持指定 NPU core mask。工程上可以给不同模型或不同 worker 创建独立 RKNN 实例，绑定到不同 NPU core，避免多个任务都挤在一个 core 上。实际分配要根据模型耗时和视频路数做压测，不是平均分就一定最优。

### 5.15 “结合线程池实现多模型并行推理”

回答：

每路视频解码后把帧提交到推理任务队列，线程池 worker 拿到任务后执行对应模型的 RKNN 推理。多模型可以并行跑，但队列要有上限，避免输入帧堆积；输出结果带上 stream id 和 frame id，便于后处理按帧合并。

### 5.16 “置信度过滤、IoM 嵌套关联、NMS 抑制及类别融合”

可直接背：

第一步 confidence filter，过滤低分框，减少后处理负担。

第二步 NMS，同类框按置信度排序，IoU 超阈值的低分框被抑制，解决重复检测。

第三步 IoM 嵌套关联，把安全帽、手机、打电话等小目标关联到人员框上。因为小目标和人员框面积差异大，用 IoU 不敏感，所以用 IoM。

第四步类别融合，根据业务规则给人员打标签，比如“person + helmet = 有安全帽”，“person + phone = 玩手机/打电话风险”。最终绘制的是融合后的业务结果。

### 5.17 “完成检测框绘制和多路画面 2x2 拼接显示”

回答：

后处理得到最终框后，用 OpenCV 或图像绘制模块把框、类别、置信度画到每路画面上，然后把四路画面 resize 到同样大小，分别放到合成画布左上、右上、左下、右下。拼接后的合成帧进入推流队列。

### 5.18 “视频合成帧队列、推流线程和丢帧控制机制”

回答：

合成帧队列是渲染线程和推流线程之间的缓冲。推流线程独立从队列取帧编码和发送；如果网络抖动或编码变慢，队列可能变长，这时会丢弃旧帧，只保留最新帧或限制最大队列长度。这样保证端到端延迟不会无限增长。

### 5.19 “通过 RTMP 推送至流媒体服务端”

回答：

RTMP 适合把实时编码后的视频推到流媒体服务端，比如 nginx-rtmp 或其他流媒体服务器。推流端需要把 H.264 packet 封装成 FLV/RTMP 格式，并维护时间戳，服务端再分发给浏览器或监控平台。

### 5.20 “技术栈：C++、FFmpeg、Rockchip MPP、RKNN、CMake、RTMP”

逐项回答：

C++：主工程语言，多线程、队列、SDK 封装、性能控制。

FFmpeg：MP4 拆包，读取视频 packet 和时间戳。

Rockchip MPP：H.264 硬解码和硬编码。

RKNN：模型转换和 NPU 推理。

CMake：组织编译、链接 FFmpeg/MPP/RKNN/RTMP 等依赖。

RTMP：把分析后的合成视频流推到服务端。

### 5.21 RK3588 项目常见拷打题

问题：FFmpeg 和 MPP 的分工是什么？

回答：

FFmpeg 负责容器层 demux，从 MP4 里拆出 H.264 packet；MPP 负责硬件解码，把压缩 packet 解成图像帧。推流端也类似，MPP 编码成 H.264，RTMP/FFmpeg 负责封装和推送。

问题：多模型并行会不会互相抢 NPU？

回答：

会，所以要做 core mask 和线程池调度。不同模型实例可以绑定不同 NPU core，任务队列也要限长。最终以压测为准，看哪个模型耗时最长，再决定是模型级并行、流级并行，还是关键模型高频、次要模型低频。

问题：NMS 和 IoM 为什么都要？

回答：

NMS 解决同一类重复框；IoM 解决不同类之间的嵌套关联。比如安全帽在人员框里，二者不是重复目标，不能用 NMS 去掉，而要用 IoM 判断归属关系。

问题：端侧部署遇到过什么坑？

回答：

常见问题包括 ONNX 动态 shape 不兼容、算子不支持、输入通道顺序和 mean/std 不一致、NPU context 线程安全、MPP 输出格式不是模型需要的 RGB、以及推流网络抖动导致队列积压。解决思路是固定输入尺寸、简化 ONNX、替换不兼容算子、明确 NHWC/NCHW 和 RGB/BGR、队列限长、各模块独立压测。

## 8. 面试中必须守住的边界

### 不能把语义分割说成 YOLO 检测

正确说法：模型做像素级语义分割，检测框是由 mask 后处理得到的可视化结果。

### 不能把显示 FPS 说成模型推理 FPS

正确说法：显示 FPS 是 UI/相机刷新速度，推理延迟是单次模型异步推理耗时。两者不同。

### 不能说 Graphene GUI 已完全动态支持

正确说法：训练/迁移代码支持 Graphene 3 类或类映射；当前桌面端默认 4 类，需要进一步做动态类别配置。

### 不能说 RepELA-Net 精度全面超过所有 baseline

正确说法：它在轻量化、模型大小、显存占用方面有优势；部分预训练 baseline 的 mIoU 更高。RepELA-Net 是无预训练 scratch 条件下的轻量模型。

### 不能把 RK3588 多路视频项目说成本地当前仓库已完整核验

正确说法：当前能拿出本地依据的是 RKNN 转换和 RKNNLite 推理部分；多路 MPP/FFmpeg/RTMP 项目按简历描述可解释实现链路，但如果面试官要代码，需要准备对应工程或说明项目环境在另一目录/设备上。

## 9. 最推荐背诵的“被拷打版”总结

如果面试官问“你这个二维材料项目到底难点在哪”，回答：

难点有三个。第一是任务本身难，二维材料单层、少层、多层差异很细，边界不明显，不能简单做目标检测，所以我用语义分割。第二是实时系统难，相机采集、UI 显示和模型推理耗时差异很大，所以我用了多线程和最新帧覆盖旧帧策略，保证界面不被推理阻塞。第三是部署和可用性，模型输出只是 mask，用户需要看到检测框、置信度、层数统计和可保存结果，所以我做了连通域后处理、类别筛选、比例尺、性能元数据保存和 AVI 录制。

如果面试官问“你这个 RK3588 项目到底难点在哪”，回答：

难点是多路视频实时性。单路视频用 CPU 解码和推理可能还能跑，多路就必须做硬件分工：FFmpeg 拆包、MPP 硬解、RKNN/NPU 推理、后处理融合、MPP 硬编码、RTMP 推流。系统还要用多线程和有界队列控制延迟，推理线程不能阻塞解码，推流网络抖动也不能把整个系统拖死。

如果面试官问“你最大的不足是什么”，回答：

我现在最需要继续加强的是大规模工程化和 C++ 生产级代码经验。已有项目里我能打通从模型到系统的链路，但像配置管理、统一推理服务接口、自动化测试、跨平台部署、日志监控这些工程化能力还可以继续提升。我已经意识到 2DMatScope 里 GUI 和模型代码耦合偏强，后续会把模型加载、滑窗推理、导出服务抽成独立模块。
